## 1. 一句话结论（三问三答）

| 我的问题 | 一句话答案 |
|---|---|
| ① `async_send_request` 返回的 **`SharedFutureAndRequestId`** 有什么用？ | 它是一个 **`{future + request_id}` 的包装**：可以**当 future 用**（等结果），也可以**用 id 取消这个还没回来的请求**（`remove_pending_request`）。**用回调版时你不需要它** |
| ② 为什么**服务回调**参数要用**智能指针**？ | 因为 **Humble 里服务回调只有 `SharedPtr` 形态**（共 4 种）；根因：**请求是 rclcpp 自己 `make_shared` 造出来的**，而且**响应允许延迟发送**（defer），只有 `shared_ptr` 能保证它活到发送那一刻 |
| ③ 为什么**订阅者**可以直接收**结构体（`const T&`）**？ | 订阅的消息是**中间件给的样本**，**回调执行期间一定有效** → 直接给引用就是**零拷贝**。代价：**出了回调就失效，不能存起来** |

## 3. 为什么会这样（原理，全部带源码）

### 3.1 `SharedFutureAndRequestId` 的真身（`client.hpp:431`）

```cpp
struct SharedFutureAndRequestId
  : detail::FutureAndRequestId<std::shared_future<SharedResponse>>
{
  using detail::FutureAndRequestId<std::shared_future<SharedResponse>>::FutureAndRequestId;
};
```
头文件注释原文：
```
 * - future: a std::shared_future<SharedResponse>.
 * - request_id: the request id associated with the future.
 * All the other methods are equivalent to the ones std::shared_future provides.
```
→ **它就是"future + 请求号"**，并且**能当 `shared_future` 用**（`wait` / `get` / `valid`）。

### 3.2 它的第二个用途：**取消请求**（这是只有它有、回调版没有的）

```cpp
// client.hpp:725
bool remove_pending_request(const SharedFutureAndRequestId & future)
{ return this->remove_pending_request(future.request_id); }   // → pending_requests_.erase(request_id)
```
→ 所以返回值**不是废的**：当你想"发出去、但不想等/想撤掉"时用它。

### 3.3 我用回调版为什么不用管返回值？（我自己的推理 ✔️ + 补一句）

```cpp
// client.hpp 的 async_send_request_impl（简化）
int64_t sequence_number;
{
  std::lock_guard<std::mutex> lock(pending_requests_mutex_);
  rcl_ret_t ret = rcl_send_request(get_client_handle().get(), &request, &sequence_number);  // 真的发出去
  if (RCL_RET_OK != ret) { throw_from_rcl_error(ret, "failed to send request"); }
  pending_requests_.try_emplace(                       // ← 【存下来】按请求号
    sequence_number,
    std::make_pair(std::chrono::system_clock::now(), std::move(value)));   // value 里含：回调 + shared_future + promise
}
return sequence_number;
```
- **我原来的推理对**：tuple 里确实**多存了一份 `shared_future`**，所以 `promise` 不会因为"没人接"而死；
- **补一句更准确的**：`std::move(promise)` 把 **promise 的所有权**搬进那个 tuple（存进 `pending_requests_` map），
  响应回来时 rclcpp 按 `sequence_number` 找到这条记录 → **调用我的回调** → 然后擦除这条记录。
  → 所以"**一问一答后回调就不再被调用**"是对的；严格说：**这一轮的 (callback+future+promise) 组合被擦掉了**，
  而**回调函数（lambda）本身还在**（每次请求都会新建一个副本）。

### 3.4 ② 服务回调为什么"只能"用 `SharedPtr`？（`any_service_callback.hpp`）

**事实**：服务回调在 Humble 里**只有 4 种形态，全是 `SharedPtr` 家族**（我 grep 出来的全部别名）：

```
203: using SharedPtrCallback
208: using SharedPtrWithRequestHeaderCallback
214: using SharedPtrDeferResponseCallback                  // ← 延迟响应
219: using SharedPtrDeferResponseCallbackWithServiceHandle
```

**根因（`service.hpp:455-492`）**：
```cpp
std::shared_ptr<typename ServiceT::Request>
create_request() override
{ return std::make_shared<typename ServiceT::Request>(); }   // ① 请求是 rclcpp 自己 new 的

void handle_request(std::shared_ptr<rmw_request_id_t> request_header,
                    std::shared_ptr<void> request) override
{
  auto typed_request = std::static_pointer_cast<ServiceT::Request>(request);
  auto response = any_callback_.dispatch(this->shared_from_this(), request_header, typed_request);
  if (response) { send_response(*request_header, *response); }   // ② 拿到 response 才发
}
```
1. **请求对象的分配方不是中间件、而是 rclcpp** → 到你手上天然是 `shared_ptr`；
2. **`dispatch` 可能返回空**（你选了"延迟响应"）→ 那就得**握着 `Response::SharedPtr` 到未来某个时刻再 `send_response()`** → **只有 `shared_ptr` 能撑到那时候**。

### 3.5 ③ 订阅为什么能收 `const T&`？

订阅回调在 Humble 里是**六大家族**（`any_subscription_callback.hpp`）：
```
ConstRefCallback（const T& ← 我用的是这个） / UniquePtrCallback（unique_ptr，零拷贝接管）
SharedConstPtrCallback / ConstRefSharedConstPtrCallback / SharedPtrCallback / +Info / SerializedMessage 变体
```
- 消息是**中间件样本**：**回调期间一定有效** → 于是 `const T&` 就够（零拷贝，最省）；
- 代价：**回调结束就失效** → **不能把引用/指针存起来**（要留就得拷贝或用 `SharedPtr` 形态）；
- 想"接管样本生命周期"就用 `unique_ptr` 形态（零拷贝 + 可以留）。

**三个可以自己设计的实验（都 5 分钟）**：
1. 订阅者里**把 `const T&` 的消息存进成员变量** → 编译能过，**运行时是野指针**（证明"回调一走引用作废"）；
2. 客户端**接住返回值**：`auto fut = add_clinet->async_send_request(req); auto r = fut.future.get();` → 能拿到结果（说明返回值可当 future 用）；
3. 客户端**取消**：`remove_pending_request(fut)` → 那条请求不再触发回调。

## 5. 要不要 / 什么时候用（判断标准）

| 场景 | 用哪个 |
|---|---|
| "发完就走"（我现在的写法） | **回调版**，忽略返回值 |
| 想**等结果**再继续（同步式） | 接住返回值：`fut.future.get()`（⚠️ 要配合 `spin`，否则死等） |
| 想**超时 / 取消** | 接住返回值 → `remove_pending_request(fut)` |
| 订阅里想**留住消息** | 拷贝一份，或改用 `SharedPtr` / `unique_ptr`（零拷贝）形态 |
| 服务里想**延迟响应** | 用 `SharedPtrDeferResponseCallback` 形态（存 `Response::SharedPtr`） |

## 7. 口诀 & 排查清单

> **口诀：订阅收样本（引用够用），服务给对象（指针才活）；回调一走引用作废，响应延后指针保命。**

| # | 症状 / 需求 | 怎么办 |
|:---:|---|---|
| 1 | 想在回调外继续用消息 | 必须**拷贝**或改用智能指针形态（不能存引用） |
| 2 | 想等结果再往下走 | `auto fut = async_send_request(req); fut.future.get();`（记得 spin） |
| 3 | 想取消已发出的请求 | `remove_pending_request(fut)` |
| 4 | 服务要"过一会儿再回" | 用 **Defer** 形态，保存 `Response::SharedPtr` |
| 5 | 收到"垃圾数据 / 段错误" | 先查：是不是**存了 `const T&` 的消息** |
